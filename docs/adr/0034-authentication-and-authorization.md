# ADR-0034: Authentication and Authorization

> **Status:** Proposed • **Date:** 2026-11-10

## 1. Context & Problem

A station records audio outdoors, where speech can end up on a recording, and it is controlled over a network other people share. Today the Gateway protects everything behind it with one HTTP Basic credential per installation, generated by `just setup`. That keeps strangers out, but it is one shared login: no accounts, no roles, no sign-out, nothing a program could use, and no record of who did what. The `users` row the Controller seeds (`admin` / `1234`) has no consumer yet.

The API ([ADR-0032](0032-api-first-station-contract.md)) has three kinds of clients with different needs: a person in a browser, a script or another service, and later a fleet. A station sold as a product must also meet the rule that EU law sets for connected devices — the Radio Equipment Directive's delegated act (EN 18031) now, the Cyber Resilience Act from 2027: no password that is the same on every unit.

## 2. Decision

**We chose:** the API service authenticates every request itself — server-side sessions in a cookie for browsers, revocable API tokens for everything else — and authorizes it against three roles. A station ships without credentials.

**Reasoning:**

*   **No default credentials.** A fresh station is in setup mode: `POST /setup` creates the first administrator and needs the station's setup code, a random value unique per unit that is printed on it or shown on its console. Whoever reaches an unclaimed station over the network cannot take it over. The seeded `users` row is removed, and the Gateway's Basic credential gives way to the sessions below.
*   **Browser: a server-side session in a cookie.** The cookie holds a random 256-bit identifier and nothing else; the database keeps its SHA-256 hash, the user, the times and the client. It is set as `__Host-Http-silvasonic_session` with `Secure; HttpOnly; SameSite=Strict; Path=/`.
    *   A script injected into the page cannot read an `HttpOnly` cookie; a token in `localStorage` it can.
    *   `<audio>`, `<img>` and `EventSource` cannot send an `Authorization` header, so clips, pictures and live events would each need a workaround with bearer tokens.
    *   Signing out, changing the password or deactivating a user ends sessions at once, because the server holds them.
    *   The cookie attributes and the forgery defence follow RFC 10017 (BCP 212), which ranks a session held by the server above every pattern that hands tokens to the page. The dashboard and the API share one origin, so OAuth has nothing to delegate.
    *   A session expires after 14 days without use and after 90 days in any case; its identifier changes at sign-in. A user sees and revokes their own sessions.
*   **Cross-site request forgery** is stopped without tokens: `SameSite=Strict`, a required custom header (`X-Silvasonic-Csrf: 1`) on every unsafe method, which a foreign page cannot send without a CORS preflight that is never granted, and a check of `Sec-Fetch-Site` / `Origin`. CORS stays closed.
*   **Passwords** are hashed with Argon2id. At least 12 characters, no composition rules, no forced rotation, common and leaked passwords refused. Failed sign-ins are slowed per account and per address with a growing delay — not locked, so that nobody can lock the only administrator out. Every failure answers alike.
*   **Scripts and services: API tokens.** `sst_` followed by 32 random bytes, sent as `Authorization: Bearer`. The station stores a hash and shows the secret once. A token has its own role, never above its owner's, an optional expiry and a last-used time; only a signed-in person creates one.
*   **Three roles.** `viewer` reads and listens. `operator` also switches microphones and modules and reviews detections. `admin` also changes settings, users, tokens and the system. Each operation declares its lowest role in the contract (`x-required-role`); the API service is the only place that enforces it.
*   **An audit log** records sign-ins, failures and every change with actor, target and outcome.
*   **The Gateway authenticates nothing itself.** For the development tools behind it, it asks the API whether the request has a valid session (`forward_auth`).
*   **Recovery needs the station.** A command on the station resets the administrator. There is no e-mail to hijack.

**Deferred, with their place reserved in the contract:** a second factor (TOTP), passkeys, and sign-in through a fleet account (OpenID Connect). `GET /info` lists the methods a station offers, so adding one is not a breaking change. Passkeys bind to a hostname and need a trusted certificate; they become possible with [ADR-0035](0035-https-and-certificates.md). How a station proves its identity to a fleet is a separate decision.

## 3. Options Considered

*   **HTTP Basic at the Gateway (as is):** Rejected. The password travels with every request, there is no sign-out, no roles, no tokens and no per-operation rule.
*   **JWT access and refresh tokens held by the page:** Rejected. A token the page can read is a token an injected script can steal; revoking one needs server state after all; media elements and `EventSource` cannot carry it.
*   **A signed, stateless session cookie:** Rejected. Listing and revoking sessions needs server state anyway, and then the signature adds only key management.
*   **An identity provider on the station (Keycloak, Authentik):** Rejected. It costs more memory than the rest of the stack to manage one or two accounts. It belongs to the fleet server, where many people and organisations sign in.
*   **Network identity only (Tailscale):** Rejected as the only method. It would leave the local network open and tie the product to one VPN. It can become an additional method.
*   **Passkeys only:** Rejected. A station reached as `silvasonic.local` has no hostname a passkey could bind to, and a lost phone would lock the owner out.

## 4. Consequences

*   **Positive:**
    *   No unit leaves with a known password; the setup flow is the same for a hobby user and a fleet.
    *   One mechanism covers pages, media, live events and third-party clients.
    *   Who may do what is readable in the contract and testable against it.
*   **Negative:**
    *   The session cookie needs HTTPS on every hostname ([ADR-0035](0035-https-and-certificates.md)).
    *   Every request looks up a session or token; the API caches the result for a few seconds, which bounds how late a revocation takes effect.
    *   12 characters is below the 15 that NIST SP 800-63B-4 asks of a password used alone. The second factor closes that gap; until it exists this is a known shortfall.
*   **On acceptance these documents change:** ADR-0023 §2.4 (default admin), US-C08, US-GW03 and US-WI01 (login criteria), `config/defaults.yml` (`auth`), `services/gateway/Caddyfile` and the password step of `scripts/setup.py`.
